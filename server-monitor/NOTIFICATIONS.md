# 障害・復旧通知

Ubuntuの異常と外部サービスの状態変化は、監視DBのイベント・送信待ちへ同時に保存する。外部サービスの観測状態は保存成功後だけ進める。Discordへ送れない間に障害が復旧しても、障害と復旧の両方を保持する。

- 送信待ちは順番に送り、成功したものだけ削除する。失敗時は60秒から最大30分間隔で再試行する。再起動でも残る。
- 通知には送信時刻とは別に記録時刻をJSTで付ける。公式障害の実際の発生時刻とは区別する。
- 異常だけロール1489628881135730852をメンションする。復旧・保守情報・定時報はメンションしない。
- 正常な初回観測は通知しない。外部サービスの公式発表は、本システムへの影響が確認できたという意味ではない。
- Ubuntuはカーネルの起動IDを保存し、変化後の最初の収集成功で「Ubuntu起動後の監視を再開しました」を送信待ちへ保存する。推定起動時刻と収集時点の状態を付け、メンションしない。初回導入は基準の登録だけを行い、監視プロセスだけの再起動ではOS再起動と扱わない。
- 管理画面・自動復旧からのサービス再起動は、操作履歴・イベント・送信待ちを同じDBトランザクションで保存する。成功はメンションなし、失敗は指定ロール付き。コマンド成功とサービスの復旧完了は区別し、稼働確認は通常監視を続ける。
- 外部状態の保存直前にプロセスが停止した場合や、Discord側が受領した直後に通信が切れた場合は通知が重複する可能性がある。未送信の記録を失うことを避ける方式。
- 定時報はJST9/10/12/16/17/20時。成功した枠を記録し重複を抑止し、枠の開始5分以内に再試行する。期間外の古い定時報は新たに生成しない。

サーバー停止はGitHub側の外形監視でも確認する。ただし実行間隔の遅れがあり、Discord自体の停止中は即時配信できない。監視で一度も観測できなかった短い外部障害の履歴まで保証するものではない。

停電・電源断の瞬間にサーバー自身から通知することはできない。起動通知から再起動の原因も断定できない。SSH等で監視を経由せず実行した個別サービスの短い再起動は、停止を観測できない場合があり、再起動操作の結果通知の対象外。

## アプリケーション処理・画面エラー（2026-11-06追加）

- PM2の監視対象8プロセスの標準出力/エラーと、Dockerの稼働対象12コンテナのログを約1分間隔で差分監視。バックアップ・退避コンテナは対象外。監視サービス自身は既存の収集失敗・外形監視を使う。
- Discord権限不足、DB/通信異常、500番台、未処理例外などを検知。原文・入力・スタックを通知へ転送せず、固定の日本語説明と対応先を通知する。新着ログを読む位置と通知待ちを同一トランザクションで保存し、再起動でも同じ障害を連投しない。
- プレス通知は2分間隔でBotの実効権限（閲覧・送信・埋め込み・添付）を読取APIで点検。既読との差分が3分以上残れば通知。取得元の30分以上の更新遅延も通知する。
- 移行した3DBのヘルスと5コンテナ・Gatewayプロセスも監視対象。DBバックアップの失敗・36時間以上の未更新、backup.logの新しい例外も対象。
- 既存の画面エラー記録から、承認済みFirebase利用者の500番台取得失敗と重大なJavaScriptエラーを、固定のシステム識別子・種類だけで業務APIへ報告する。HTTP 401/403、一般の入力不備、既知の拡張機能由来エラーは新通知の対象外。受付は認証・512バイト制限・システム/種類の許可リスト・利用者/種類ごとの10分抑止あり。生ログ・URL・利用者ID・入力内容は通知へ送らない。
- 画面報告の通信失敗時は種類だけを端末へ最大20件保留し、再接続・次回起動・約1分ごとの再試行で送る。Discord側の不通は既存の永続送信待ちへ保持する。
- 通知先は既存の監視チャンネル1499762805065388274。異常だけ1489628881135730852をメンション。復旧・確認通知はメンションなし。既存の一時停止/通知条件も尊重する。
- 権限・滞留・バックアップ等の状態確認で正常を確認した場合は復旧通知。ログしか根拠のないエラーは10分間新規エラーがなければ「再発観測なし」と知らせ、原因解消・操作成功を断定しない。

監視は記録されたエラーと既知の取得先を対象とする。エラーを記録しない処理、認証前の画面停止、更新前のキャッシュ画面、検査対象外の別サーバーまで自動で網羅するものではない。端末もDiscordも不通中の即時通知はできない。

失敗したsystemdサービスの通知には件数に加え、用途の日本語名・unit名・終了理由を記載する。非公開時刻表同期の路線名検証失敗は、対応表の確認が必要と表示する。journal原文は通知しない。ログ監視上限の警告は「監視範囲の注意」、読取再開は「監視の再開」と表記し、サービス停止・復旧と混同しない。
